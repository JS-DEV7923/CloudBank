# CloudBank Technical Architecture

Source inputs: `PRD.md`, `engineering-spec.md`, `requirements.md`, `acceptance-criteria.md`, `technical-constraints.md`, `security-requirements.md`, `observability-requirements.md`, `integrations.md`, `technical-risks.md`.

## 1. Architecture Summary

CloudBank is a modular Spring Boot REST API backed by PostgreSQL. The system uses a single deployable backend service with layered internal modules for API, security, business logic, persistence, idempotency, exception handling, documentation, and observability.

The architecture intentionally remains a monolith because the MVP has one bounded product domain, one data owner, no external banking integrations, and strong transactional consistency requirements for money movement. PostgreSQL is the system of record for users, accounts, transfers, transaction history, and idempotency records.

## 2. Goals

- Provide a secure versioned REST API for authentication, accounts, deposits, withdrawals, transfers, and transaction history.
- Preserve financial consistency through database transactions, decimal-safe arithmetic, and row-level locking.
- Prevent duplicate money movement through idempotency keys.
- Keep account and transaction access scoped to the authenticated user.
- Make the system easy to review through OpenAPI, tests, CI, Docker Compose, and Terraform-scoped AWS infrastructure.
- Support local development and cloud practice without claiming real banking compliance.

## 3. Non-Goals

- Real banking networks, ACH, cards, wires, or external ledgers.
- KYC, AML, fraud detection, credit scoring, or regulatory compliance.
- Frontend application.
- Multi-currency MVP.
- Event-driven ledger replication.
- Refresh tokens, password reset, rate limiting, and production secrets manager integration.

## 4. System Boundaries

### In Scope

- CloudBank API process.
- PostgreSQL database owned by CloudBank.
- JWT authentication implemented inside the API.
- OpenAPI documentation generated by the API.
- Local Docker Compose runtime.
- GitHub Actions CI.
- Terraform architecture for AWS ECS Fargate and RDS PostgreSQL.

### Out of Scope

- External payment providers.
- Customer support/admin back office.
- Third-party identity providers.
- External notification providers.

## 5. Actors

- Anonymous user: can register and log in.
- Authenticated user: can manage their own accounts and initiate money movement.
- Developer/reviewer: runs the service locally, reviews docs, and runs tests.
- CI system: builds and tests the project.
- AWS runtime: runs the API container and PostgreSQL database when infrastructure is applied.

## 6. Runtime Architecture

The MVP uses one Spring Boot application:

- REST controllers handle HTTP routing and DTO validation.
- Spring Security authenticates JWTs and sets authenticated user context.
- Services own business rules, authorization checks, transactions, and idempotency orchestration.
- Repositories use Spring Data JPA for PostgreSQL access.
- Global exception handling produces stable error responses.
- OpenAPI exposes generated API documentation.
- Observability filters add correlation IDs and request logs.

## 7. Trust Boundaries

- Public internet or local client to API: untrusted boundary; all input must be validated.
- API security filter to authenticated service layer: authenticated boundary; authorization still enforced per resource.
- API to PostgreSQL: trusted private network boundary in AWS; database credentials are secret.
- GitHub Actions to repository: build boundary; secrets should not be required for unit/integration tests.
- ECS to RDS: private network boundary restricted by security groups.

## 9. Major Flows

### Registration and Login

1. Client submits registration or login request.
2. Controller validates request.
3. Auth service hashes password for registration or verifies password for login.
4. User repository persists or loads user.
5. JWT service signs access token for successful login.
6. Controller returns response without sensitive fields.

### Authenticated Account Request

1. Client sends JWT.
2. Security filter validates token and resolves user identity.
3. Controller delegates to service.
4. Service performs ownership check.
5. Repository reads or writes account data.
6. Response DTO is returned.

### Money Movement

1. Client sends JWT, request body, and `Idempotency-Key`.
2. Security filter authenticates user.
3. Controller validates DTO and required header.
4. Idempotency service checks existing key and request hash.
5. Money movement service starts transaction.
6. Account rows are locked in deterministic order.
7. Balance and transaction records are updated atomically.
8. Idempotency record stores response metadata.
9. Response is returned.

## 10. Assumptions

- MVP currency is `USD`.
- Account IDs use UUIDs; account numbers are separate unique generated numeric strings.
- Cross-user resource access should return `404 Not Found` to avoid resource disclosure, unless implementation chooses `403` for explicit portfolio clarity.
- Idempotency records do not expire in MVP.
- Testcontainers PostgreSQL is preferred for integration tests.
- Spring Actuator is optional but recommended for health and metrics.
